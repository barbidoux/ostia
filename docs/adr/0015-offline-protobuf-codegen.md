# ADR-15: Offline Protobuf code generation with protox/prost (Rust) and grpcio-tools (Python)

- Status: proposed
- Date: 2026-10-05
- Deciders: Matthias Vaytet (owner), to accept; dependencies approved in Q-18 and Q-20, lint exceptions
  for generated code in Q-19 and Q-21
- Source: ADR-03 (follow-up "the codegen path is chosen and recorded in WP-0.5"), prompts/P0.md WP-0.5

## Context and problem statement

The `ostia.engine.v1` contract (`proto/ostia/engine/v1/engine.proto`) must be usable from the Rust core and
the Python workers. Machines have no `protoc` or `buf` installed, the kiosk build must not download tools,
and every generated artefact must stay checkable against the `.proto`.

## Decision drivers

- Offline and reproducible: dependencies only from the package registries, pinned exactly.
- No system tool to install on developer machines, CI or the bench.
- Generated code is typed (Rust types, mypy-strict stubs) and cannot drift from the `.proto` unnoticed.
- Lint and type gates stay strict on hand-written code.

## Considered options

1. Rust: prost + prost-build with protox (a Protobuf compiler written in Rust) in `build.rs`. Python:
   `protobuf` runtime; code generated by the protoc bundled in `grpcio-tools`, typed stub by the
   `mypy-protobuf` plugin; both committed and checked.
2. `buf generate` with local plugins (needs `buf` and `protoc` installed everywhere).
3. Python classes built at run time from a descriptor (no generated code, but untyped for mypy).

## Decision outcome

Chosen option 1.

- **Rust:** `crates/contracts` (package `ostia-contracts`) compiles the `.proto` in `build.rs` with
  protox 0.9.1 and generates the types with prost-build 0.14.4; the runtime is prost 0.14.4. Nothing is
  committed; every build regenerates from the `.proto`. clippy's `must_use_candidate` and `doc_markdown`
  are allowed on the generated module only (prost's helpers trip them; Q-21).
- **Python:** `tools/contracts/gen_python.py` (`just proto`) runs `python -m grpc_tools.protoc`
  (grpcio-tools 1.84.0, dev only) with the `protoc-gen-mypy` plugin (mypy-protobuf 5.1.0, dev only) and
  writes `engine_pb2.py` and `engine_pb2.pyi` to `workers-py/common/src/ostia_common/engine_v1/`.
  They are committed (workers run without the generator); `gen_python.py --check` and a tooling test fail
  when they no longer match the `.proto`. ruff excludes the two generated files (Q-19); mypy checks them
  through the stub. The runtime is protobuf 7.36.2.
- **Compatibility (CTR-04):** `buf breaking` is not available; `proto/ostia/engine/v1/compat.json` freezes
  every v1 field and enum value, and tests check the generated descriptors against it. The committed golden
  vectors (`proto/testdata/`) are the compatibility tests later minors must still decode.

## Consequences

- Good: `cargo build` and `uv sync` are enough; no tool to install; CI and the bench need nothing extra.
- Good: generated Python code is reviewed in diffs and cannot drift silently.
- Bad: two generators (protox for Rust, protoc for Python) could disagree on edge cases; the shared golden
  vectors catch any difference in the encoding.
- Bad: no `buf lint`; the `.proto` style is kept by review and `compat.json`.
- Follow-ups: package `workers-py/common` as a uv workspace member when the Python worker framework is
  built (WP-2.3); until then it is on the pytest and mypy paths.
