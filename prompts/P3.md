# P3 · Engines — phase brief

**Goal.** Add the built-in engines (ClamAV, YARA-X, reputation, Office/PDF/PE heuristics) and the
plug-in SDK (signed manifests, native/CLI/ICAP adapters, trust levels, conformance kit) that lets anyone
add an antivirus without touching the core.
**Exit gate.** `tests/acceptance/p3/` green and unchanged; mutation score ≥ 70 % on the verdict policy
(NFR-14); the conformance kit certifies every built-in engine; P4 tests locked.

## Entry checks
- P2 gate ticked, `lock-p3` tag, verify passes.
- Tools in the dev container and CI: `clamav-daemon` (clamd), `c-icap` and its ClamAV module
  (`c-icap-modules` or equivalent), `upx-ucl`, `osslsigncode`, `mingw-w64` (to build tiny Windows test
  binaries from source), `cargo-mutants`. Missing ones: ask the owner 👤.

## Order
WP-3.1 → WP-3.2 → (WP-3.3 ‖ WP-3.4 ‖ WP-3.5 ‖ WP-3.6 ‖ WP-3.7 ‖ WP-3.8 ‖ WP-3.9 ‖ WP-3.10)
→ WP-3.11 (after 3.3, 3.4) → WP-3.12 → WP-3.13 (lock P4).

## Package guidance

### WP-3.1 Engine manifest
- `schemas/engine-manifest.schema.json` (published, CTR-06): identity, adapter (native/cli/icap), file
  types, trust level, sandbox profile, limits, verdict mapping (vendor result → hint, unwanted-software
  categories), update hook, licence notice, content-version source. TOML on disk, validated against
  the JSON schema after parsing; detached Ed25519 signature over exact bytes.
- Errors are precise (field path + reason); one test per invalid case.

### WP-3.2 Engine host
- Loads `engines/*.toml` (+ `.sig`), instantiates adapters, runs every applicable engine per object in
  parallel within bounded concurrency. Trust levels: `alone` (one detection → R2), `vote` (K-of-N among
  vote engines → R2; fewer → R6), `advisory` (only findings, never a verdict by itself). Map vendor
  categories (PUA, adware, tool) per engine to hints.
- NFR-13 test: a new fake engine added by dropping a manifest in a temp `engines/` dir changes the results
  with no code change.

### WP-3.3 CLI adapter
- Command template with placeholders for the object path inside the sandbox (fd 3 exposed as
  `/proc/self/fd/3` or a bind-mounted read-only file), exit-code mapping and output parsing by regex
  declared in the manifest. Runs in the sandbox like any worker (SEC-13). Hang → TIMEOUT, garbage → ERROR.

### WP-3.4 ICAP adapter (RFC 3507 client)
- OPTIONS (cache `Max-Connections`, `Preview`, `Transfer-Preview`), RESPMOD with encapsulated HTTP response
  carrying the object, preview + `100 Continue`, `204 No Content` = clean, infection headers
  (`X-Infection-Found`, `X-Violations-Found`, vendor variants declared in the manifest).
- The ICAP server runs in its own loopback-only network namespace (ENG-03); the client connects only there.
- Test first against a fake ICAP server (Python, in `tests/fakes/`) replaying recorded exchanges: infected,
  clean, error, timeout; then against c-icap + ClamAV in CI.

### WP-3.5 ClamAV via clamd
- Local Unix socket; config with `ConcurrentDatabaseReload no`, `MaxScanSize`/`MaxFileSize` aligned with
  Ostia limits; send the object with `FILDES` (passes fd 3 over the socket with SCM_RIGHTS) or `INSTREAM`
  (chunked); parse `<name>: <sig> FOUND` / `<name>: OK` / `... ERROR`, where `<name>` is `stream` for
  INSTREAM and `fd[<n>]` for FILDES (check against the clamd version in use).
- Tests run clamd offline with a **custom database containing only an EICAR signature** (`.ndb` or `.hdb`
  written at test time) so it starts in seconds; EICAR itself is built at runtime from two halves.
- clamd down or unresponsive → every object UNSCANNABLE (R1), clearly reported.
- RAM: document 3–4 GiB for real databases (spec risks).

### WP-3.6 YARA-X worker
- `yara-x` crate (BSD-3-Clause). Rule bundles compiled at build time; each rule set declares a licence
  (manifest) — a rule set without one fails the build. Severity from rule `meta: severity = "critical|high|..."`;
  critical → R2, others → findings feeding R6 per policy.

### WP-3.7 Reputation worker
- Known-bad: MalwareBazaar hash lists imported from signed bundles (never fetched at runtime; tests use a
  tiny synthetic list). Known-good: NSRL-derived bloom filter (CIRCL hashlookup format or own); tests build
  a tiny bloom at test time. Mind false positives of bloom filters: known-good must be confirmed by an exact
  set or accept a documented FP rate — 👤 decide (R3 overrides ML, so FPs matter).

### WP-3.8 Office heuristics (oletools)
- `olevba`, `mraptor`, `msodde`, `oleobj` as libraries inside the worker. Findings: auto-exec macro, suspicious
  keywords, DDE, embedded objects, external relationships (template injection).
- Test documents generated at test time: DDE in DOCX/RTF is plain XML/text; an auto-run macro needs a
  `vbaProject.bin` — if it cannot be generated without Office, use a harmless macro project from a
  permissively licensed test corpus (oletools test files, check licence) committed as a fixture with its
  origin and hash documented 👤 confirm.

### WP-3.9 PDF heuristics
- `pikepdf` (MPL-2.0 — check allowlist) or a pure-Python parser: JavaScript (`/JS`, `/JavaScript`),
  `/OpenAction`, `/AA`, `/Launch`, embedded files, `/URI` counts, object-stream oddities.
  Test PDFs generated at test time with harmless `app.alert('ostia-test')`.

### WP-3.10 PE heuristics
- `pefile` for sections and entropy; `signify` for Authenticode (validity, chain to a test root, timestamp).
- Test binaries built at test time: tiny C program cross-compiled with `x86_64-w64-mingw32-gcc`, signed with
  `osslsigncode` using a throwaway certificate generated in the test, packed with `upx` for the packer case.

### WP-3.11 Conformance kit `ostia engine certify`
- Criteria (ENG-04): EICAR detected; clean corpus with no detection; correct timeout behaviour; crash and
  malformed-input handling; concurrent load; version reporting (CTR-03); offline content update applied.
  One fake engine per broken criterion must fail with that criterion named.
- Health (ENG-07): version, content age, last self-test; policy option to refuse scanning when a required
  engine's content is older than a threshold.

### WP-3.12 Cascade tuning and mutation testing
- `cargo mutants` on the policy module (`crates/core-domain` policy path); CI fails below 70 %. Missed mutants
  → add table rows (tests), never exclude code from mutation without the owner 👤.
- Cascade: hash reputation first, then fast engines in parallel; measure and record.

### WP-3.13 Lock: P4 acceptance tests → `/phase-lock P4`
P4 tests are mostly **bench** tests (Debian machine with `dummy_hcd` and configfs gadgets, real drives).
Cover: plain storage gadget allowed; HID + storage composite blocked (USB-01, D1); internal device allowed
only by exact identity, port and descriptor hash (USB-02); class-liar gadget gets no driver (USB-03, SEC-07);
re-enumeration mid-scan aborts the session and discards results (USB-04); fingerprint logged (USB-05);
multi-configuration device raises a finding (USB-06); mount is `ro,noexec,nosuid,nodev` and injection refused
(FR-02, SEC-08); workspace unreadable after session end and after a crash (FR-20, SEC-11); input device
refused as output, unknown output refused, bit flip during copy detected (FR-13, SEC-09, USB-08); signed
transfer manifest verifies and any edit breaks it (FR-22, CTR-05); only the helper privileged, separate
accounts, workspace non-executable (SEC-06, SEC-12, NFR-10); end-to-end with real FAT/exFAT/NTFS drives
(FR-01, exit criterion). Bench tests fail (not skip) without hardware; the README says how to run them.
Contracts first: bench device naming (`OSTIA_BENCH_DEVICE`, gadget names), manifest schema
(`schemas/transfer-manifest.schema.json`), CLI for the transfer step.
