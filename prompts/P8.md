# P8 · Enrichment — phase brief

**Goal.** Optional online analysis without weakening the offline posture: provider interface, VirusTotal
provider (hash lookup, upload, Private Scanning), policy settings and deployment profiles, quota-aware
asynchronous scheduler with rule E1 and post-transfer alerts, enrichment dialog, offline export/import with
`ostia-enrich`, relay client, key storage and logging.
**Exit gate.** `tests/acceptance/p8/` green, unchanged; no upload possible outside the configured mode;
every ENR requirement green; P9 tests locked.

## Absolute rules for this phase
- **Tests never call the real VirusTotal API**, nor any other live service. They use the fake provider and
  recorded responses committed as fixtures (sanitised: no real key, no real customer hash unless public).
  The guard hook blocks shell access to virustotal.com and malware repositories.
- The project ships no API key (ENR-09). The free public API's terms forbid use in business workflows,
  commercial products or services: the documentation says so and organisational deployments need a licence.
- Enrichment is off by default; the regulated profile is the default profile; an enrichment result can only
  raise a verdict.

## Entry checks
- P7 gate ticked, `lock-p8` tag, verify passes.
- Recorded responses: 👤 the owner may record a few real responses once, by hand, outside the agent, with his
  own key, for public test hashes (e.g. EICAR's SHA-256) and sanitise them; otherwise build fixtures from the
  public API documentation examples. The agent never handles the real key.

## Package guidance

### WP-8.1 Provider interface and fake provider (`crates/enrich`)
- Trait: `lookup_hash`, `upload` (standard or private), `poll_analysis`, `quota`, `capabilities`
  (private scanning, password support). Errors: not found, quota exceeded (with retry-after), timeout,
  server error, auth error. The fake provider (from WP-0.7) scripted per hash.
- A shared contract-test suite that every provider must pass (run against the fake now, against VT recorded
  responses in WP-8.3).

### WP-8.2 Policy settings and profiles
- `enrichment.enabled` (default false), `enrichment.upload` ∈ {`disabled`, `admin_approval`, `user_choice`},
  `enrichment.deny_types` (office documents in the regulated profile, empty in the community profile),
  `enrichment.e1_threshold` (N, default 3 — open question 👤), provider mode (`offline_export`, `relay`, `direct`).
  All inside the signed policy (ENR-13); a missing profile means regulated defaults; changes require a
  super-administrator and are logged.
- Table tests: every mode × every file type × deny list → allowed actions.

### WP-8.3 VirusTotal provider
- API v3: `GET /api/v3/files/{hash}` (404 = not found), `POST /api/v3/files` (or `upload_url` for large files),
  `GET /api/v3/analyses/{id}`; Private Scanning endpoints under `/api/v3/private/...`; header `x-apikey`.
  Handle 429 (quota) and 5xx with backoff. Parse `last_analysis_stats` and per-engine results into findings.
- Verify endpoint paths and fields against the official documentation at implementation time (they evolve);
  record the doc version/date in the fixtures README.
- ZIP password only with Private Scanning (ENR-10, MAY).

### WP-8.4 Scheduler, E1, post-transfer alert
- Token buckets per provider (requests per minute/day from configuration), priority UNSCANNABLE > SUSPICIOUS >
  others, asynchronous results matched to sessions and transfers by object hash and manifest id.
- E1: ≥ N detections → MALICIOUS, never downgrade (property test: for any prior verdict and any result, the new
  verdict is ≥ the old one). Late detection on a transferred file → post-transfer alert carrying the manifest id
  (ENR-06), OCSF Detection Finding.
- NFR-19: local verdicts and session completion never wait on enrichment (test with an unreachable and a throttled
  fake provider).

### WP-8.5 Enrichment dialog
- Hash lookup preselected; upload option shown only when the mode allows it; sharing warning (file, size, type,
  provider, shared or private) before any upload; admin approval flow in `admin_approval` mode (UI-09).

### WP-8.6 Offline bundles and `ostia-enrich`
- Export bundle signed by the kiosk (hashes and, if allowed and approved, files encrypted to the analyst key);
  `tools/ostia-enrich` (Rust CLI) imports it on a connected analyst machine, queries the provider, writes a result
  bundle signed by the analyst key; the kiosk imports it and checks the signature (ENR-12). Schemas published
  (CTR-07). Tampering refused both ways.

### WP-8.7 Relay client and direct mode
- Relay: the kiosk calls the central platform (`enrichment:lookup` on the fake platform) over mutual TLS and never
  holds the provider key. Direct mode: an egress allowlist (nftables rules generated for the provider host only)
  and allowed only in a profile that permits it (NFR-08); test that other destinations are unreachable.

### WP-8.8 Key storage and logging
- Key encrypted at rest (key-encryption key from a local secret store or TPM later — ADR), shown once at entry,
  never logged (test greps every log and report for a planted fake key), absent in relay mode. SEC-14: the
  enrichment service reads only files explicitly approved for upload (separate directory, permissions tested).
- Every request and result logged: what (hash or file), provider, chosen by, approved by, result (ENR-11).

### WP-8.9 Lock: P9 acceptance tests → `/phase-lock P9`
P9 tests must cover: TUF repository with per-engine delegated roles — a bundle signed by one engine's key cannot
carry another engine's content (ENG-06, UPD-03), root rotation with M-of-N; older bundle refused for every
component (UPD-02); altered bundle refused and logged (UPD-01); failure midway leaves the previous version
running (UPD-04, FR-18); modified binary, policy or configuration detected at boot and the kiosk stops safely
with a logged reason (UPD-05); release job fails without an SBOM, SBOM and hashes shipped (UPD-06); two builds of
the same commit compared (UPD-08, SHOULD); hardening checklist script fails on a deliberately weakened image;
every configuration key documented (script); NFR-01 and NFR-03 performance benches are "verified elsewhere"
(WP-9.6) unless the owner wants them black-box.

## Owner checkpoints in P8
Recorded responses, E1 threshold, key-protection ADR, direct-mode policy, P9 tests review and lock, gate.
