# P2 · EMBER engine — phase brief

**Goal.** Harden the sandbox (namespaces, seccomp, cgroups v2) and ship the first real engine:
LightGBM EMBER2024 through `thrember`, in a signed model bundle, calibrated on a clean corpus,
with explanations.
**Exit gate.** `tests/acceptance/p2/` green and unchanged; inference under 10 ms per file on the
reference machine (NFR-02); thresholds shipped in the signed bundle; P3 tests locked.

## Entry checks
- P1 gate ticked, `lock-p2` tag exists, verify passes.
- 👤 Owner tasks before WP-2.4: decide the reference machine for budgets; fetch the EMBER2024 models
  once (`just fetch-models`, which you write in WP-2.4 but the owner runs) and record their hashes;
  confirm the models' licence allows redistribution in a bundle (if not: the bundle references a
  hash and the deployer fetches the model — stop and ask).
- 👤 Clean corpus: the owner decides its composition (Debian binaries, Windows system files from a licensed
  machine, PDFs, APKs). It stays local (never committed); a manifest of hashes and sources is committed.
- 👤 Ask the Debian bench machine to be ordered now if it is not (P4 needs it).

## Order
WP-2.1 → WP-2.2; WP-2.3 in parallel with WP-2.1; WP-2.4 (after 2.3) → WP-2.5 (after 2.4 and 2.1)
→ WP-2.6, WP-2.7, WP-2.8 → WP-2.9 → WP-2.10 (lock P3).

## Package guidance

### WP-2.1 Sandbox (`crates/sandbox`)
- bubblewrap first (ADR-04): `--unshare-all` (user, ipc, pid, net, uts, cgroup; never add `--share-net`),
  `--die-with-parent`, `--new-session`, `--ro-bind` a minimal root
  (`/usr`, `/lib*`, the worker binary or venv), `--tmpfs /tmp` (size-limited), `--proc /proc`,
  `--dev /dev` (minimal), `--clearenv` plus an explicit environment, `--cap-drop ALL`, and
  `--seccomp <fd>` with a BPF program built by `seccompiler` (allowlist per worker profile).
- Pass the object as fd 3 through bwrap (inherit only that fd; `close_range` everything else).
- One sandbox root per medium (SEC-02): a per-session directory tree for tmpfs/state, deleted at the end.
- Probe workers for tests (in `tests/fakes/`): try `socket()`, connect to 127.0.0.1, write outside tmpfs,
  read the workspace, read another session's files; each attempt must fail and the probe reports it.
- Pitfalls: WSL kernels support user namespaces but check `kernel.unprivileged_userns_clone` and AppArmor
  restrictions on Debian/Ubuntu (`kernel.apparmor_restrict_unprivileged_userns`); Python workers need more
  syscalls than Rust ones — derive profiles by tracing (`strace -f -c`) on the test corpus, then lock them.

### WP-2.2 Resource limits (cgroups v2)
- Each worker in its own cgroup leaf: `memory.max`, `memory.swap.max = 0`, `pids.max`, `cpu.max`,
  plus write size via tmpfs size and duration via the host timeout. Use systemd delegation
  (`systemd-run --user --scope -p Delegate=yes` for the orchestrator's slice in dev; a `Delegate=yes` unit
  in P4) and write cgroup files directly from the `sandbox` crate.
- OOM kill → read `memory.events` (`oom_kill`) → `ERROR` with reason "memory limit" → UNSCANNABLE via R1.
- Tests: memory hog, fork bomb, disk filler, CPU spinner each killed; the orchestrator stays responsive
  and the session completes.

### WP-2.3 Python worker framework (`workers-py/common`)
- Framing from WP-0.5 golden vectors, fd 3 input, structured errors, a `run_worker(handler)` entry point,
  and a pytest harness that runs a worker as a subprocess exactly as the host does.

### WP-2.4 Model bundle
- Layout: `manifest.json` (model id, version, per-format files, feature dimension 2568, thresholds,
  hashes, thrember version, created), model files, `manifest.sig` (Ed25519 over the exact bytes).
- `tools/models/fetch.py` (owner-run): downloads pinned model files by URL and verifies SHA-256 from
  `models/lock.json`; never run in CI. CI uses a tiny synthetic LightGBM model trained at test time on
  random 2,568-dimensional vectors for the bundle and routing tests.
- Refusals: unsigned, tampered (any file hash mismatch), wrong dimension, unknown format key.

### WP-2.5 EMBER worker
- Pin `thrember`, `pefile`, `lightgbm`, `numpy`, `signify==0.7.1` (known-good pin, see risks), and
  `polars` if thrember needs it — check `polars` runs on the reference CPU (some builds need AVX2; use
  `polars-lts-cpu` otherwise). Hash-pin everything.
- Route by detected type: PE (32/64, .NET), ELF, PDF, APK → their model; unknown → UNSUPPORTED.
- Frozen reference predictions: compute once with the real models on a small set of **feature vectors**
  (not binaries) and commit vectors + expected scores; tolerance 1e-9 on raw scores.
- Truncated or corrupted PE → `ERROR`/UNSCANNABLE, never a score.

### WP-2.6 Explanation
- `booster.predict(X, pred_contrib=True)` returns one contribution per feature plus the bias in the last
  column; their sum equals the **raw** score (`raw_score=True`), not the probability. Test exactly that.
- Map feature indices to readable labels (a table in the bundle, versioned with the model); every top
  factor must have a label (test).

### WP-2.7 Calibration tool
- `tools/calibrate/`: run the clean corpus through the worker, then choose `high` (target FPR, e.g. 0.1 %)
  and `low` (e.g. 1 %) thresholds — 👤 the owner sets the target FPR (open question in the spec).
- Deterministic: same scores → same thresholds; ties and small corpora handled explicitly; write the
  thresholds into a new bundle version (re-signed by the owner's key — the tool prepares, the owner signs 👤).
- Tests on synthetic score distributions with known quantiles.

### WP-2.8 Performance
- `pytest-benchmark` (or a Rust `criterion` harness if inference moves to Rust later): inference only,
  feature extraction excluded, model preloaded, `num_threads=1` per worker. Fails above 10 ms on the
  reference machine; in CI on other hardware, record but do not gate (document how).
- Profile feature extraction and size the process pool (cores, memory per worker).

### WP-2.9 Policy integration
- R4/R5 with the real thresholds; the verdict log carries model id, hash and thresholds (NFR-17).
- End to end: clean system binaries → CLEAN; a test bundle with lowered thresholds forces SUSPICIOUS and
  MALICIOUS.

### WP-2.10 Lock: P3 acceptance tests → `/phase-lock P3`
P3 tests must cover: EICAR (built at runtime) → MALICIOUS via ClamAV and R2; `clamd` down → every object
UNSCANNABLE; YARA-X marker rule fires, a critical rule triggers R2; known-bad hash → MALICIOUS; known-good
(NSRL test bloom) beats an EMBER detection (R3) but never a ClamAV detection; Office document with a
harmless auto-run macro and a DDE field → SUSPICIOUS (R6); PDF with harmless JavaScript/OpenAction →
SUSPICIOUS; UPX-packed clean binary → packer finding; signed vs unsigned clean binaries distinguished;
engine manifests (invalid and unsigned refused, ENG-01, CTR-06); trust levels alone / K-of-N / advisory
driving R2 and R6 (ENG-05); a fake CLI scanner and a fake ICAP server pass `ostia engine certify`, and one
broken fake engine per conformance criterion fails it (ENG-02, ENG-03, ENG-04); adding a fake engine needs
only a manifest (FR-23, NFR-13); third-party engine crash/timeout handled like any worker with no extra
privilege (SEC-13); engine health with version and content age (ENG-07); no commercial engine shipped
(ENG-08: a structural test over `engines/`). Mutation score (NFR-14) is "verified elsewhere" (WP-3.12).
Contracts first: engine manifest schema (`schemas/engine-manifest.schema.json`), `ostia engine certify`,
`ostia engine list --health`, report fields for engine findings.
