# P0 · Foundations — phase brief

**Goal.** Build the rails: repository, toolchains, contracts, traceability, supply-chain gates,
test doubles, decision records, and the locked P1 acceptance tests.
**Exit gate.** CI green; `tests/acceptance/p1/` (and `common/`) written, reviewed, locked and tagged.
P0 has no acceptance directory of its own: each package's own tests are its proof.

**Start a package:** `/wp-start WP-0.x`. **Owner commands** are marked 👤.

## Entry checks
- Bootstrap done (`prompts/00-bootstrap.md`): kit self-test green, environment table reviewed,
  missing tools installed by the owner.
- `main` holds the kit as its first commit. A remote exists (GitHub) or the owner said to work locally.

## Order
1. WP-0.1 → then in parallel-friendly order: WP-0.2, WP-0.3, WP-0.5, WP-0.8, WP-0.10.
2. WP-0.4 (after 0.3) → WP-0.9 (after 0.4).
3. WP-0.6 and WP-0.7 (after 0.5). WP-0.11 (after 0.2, time-boxed spike).
4. WP-0.12 last (after 0.4 and 0.9): write the P1 acceptance tests.

## Package guidance

### WP-0.1 Repository skeleton
- Cargo workspace at the root (`resolver = "2"`, `[workspace.package]` with `license = "Apache-2.0"`,
  `edition = "2021"` or the current edition, `[workspace.lints]` with `unsafe_code = "forbid"` and clippy
  groups). A workspace needs a member: create `crates/core-domain` as an empty library with a doc comment.
- `rust-toolchain.toml`: pin the exact current stable version (`rustc --version`), components
  `rustfmt`, `clippy`, `llvm-tools-preview`.
- `uv` project at the root (`pyproject.toml`, Python 3.12) with `workers-py/common` as the first member
  later; dev dependencies: pytest, hypothesis, ruff, mypy, jsonschema, pytest-cov, cryptography.
  Register pytest markers `req`, `bench`, `slow` and `--strict-markers` in `[tool.pytest.ini_options]`.
  Do not put `-m "not bench"` in `addopts`. Set `testpaths` to the unit/tooling/worker test directories
  so `just test` never collects `tests/acceptance/` (acceptance runs only through `just test-acceptance`).
- Exclude the kit from the project's linters and type checker: ruff `extend-exclude` and mypy `exclude`
  for `.claude/`, `tools/kit/`, `tools/lock/` (they are owner-managed and already checked by the kit tests).
  The guard will ask the owner to approve these exclusions: say why in the request.
- `justfile`: keep the `import 'tools/kit/rails.just'` line (rails recipes: `kit-test`, `req`, `verify-locks`,
  `rails-verify`, `lock-status`, `gate`, `acceptance-collect`, `acceptance-dry-run`, and the owner-only
  `lock`, `relock`, `rails-update`). Add `check`, `fmt`, `lint`, `test`, `test-rust`, `test-py`,
  `test-acceptance <dir>` (calls `acceptance-dry-run`), `test-bench`, `coverage`, `trace` (placeholder until
  WP-0.4), `audit` (placeholder until WP-0.8).
  `check` = fmt-check + lint + types + tests + verify-locks + rails-verify + kit-test (+ trace and audit
  once they exist). Edit the justfile with the Edit tool only (shell writes to it are blocked).
  Empty suites must pass: `cargo nextest run --no-tests=pass`, and treat pytest exit code 5 as success
  only when the directory has no tests.
- Pre-commit with the `pre-commit` framework (run via `uvx pre-commit`): rustfmt check, ruff, ruff-format,
  `python3 tools/lock/ostia_lock.py verify` and `rails-verify`, and a **commit-msg** hook enforcing
  `^(test|feat|fix|refactor|docs|chore|contract|build|ci|perf)(\([A-Za-z0-9.,\- ]+\))?: .+`.
- `LICENSE` (Apache-2.0 full text), `NOTICE`, `SECURITY.md` (private disclosure address: ask the owner),
  `CODEOWNERS` is provided by the kit (owner fills in his handle), `CHANGELOG.md` (Keep a Changelog),
  `README.md` (short: what, status "pre-alpha", licence, link to docs), `.gitignore` (provided; extend).
- CI (`.github/workflows/ci.yml`, workflow and job named `ci`): checkout, toolchains with caching,
  `just check`. Keep the kit's `rails.yml` untouched. Acceptance policy in CI: locked directories of
  **closed** phases run with `just gate <dir>` and are blocking; the **current** phase's directory runs with
  `just test-acceptance <dir>` as an informational job that publishes "N/M green" (the one justified
  `continue-on-error`); directories of **future** phases (locked during the previous phase) are not run.
  Read the current phase from `docs/phase-status.md`. Any skipped test in a non-bench run fails CI
  (parse the JUnit XML: `skipped > 0` → fail; `-m "not bench"` deselects, it does not skip).
- Tests first: the "seeded bad sample" tests live in `tests/tooling/` (pytest): each copies a deliberately
  bad snippet into a temporary crate or module and asserts that `cargo fmt --check`, `cargo clippy -D warnings`,
  `ruff` and `mypy --strict` each fail on it. These are `req("NFR-09")`/`req("NFR-15")` tests
  (check the wording with `req.py`).
- Pitfall: do not create every crate from the target layout now. Create directories when a package needs them.

### WP-0.2 Dev environment
- `tools/dev/setup-debian.sh`: idempotent apt installation of the toolchain list from the bootstrap,
  printing versions; `--check` mode only verifies. Never run it with sudo yourself: ask the owner 👤.
- `.devcontainer/` + a CI image (Debian stable) with the same tool versions. Pin versions.
- Loop-mount helpers for development: `tools/dev/mkimage.sh` (create an image of a given type and size)
  and `tools/dev/loopmount.sh` with two modes: `ro` (attach read-only + mount `ro,noexec,nosuid,nodev`
  under `target/mnt/<name>`, used by the scan) and `rw-image` (mount a regular image file located under
  `target/fixtures/` read-write, used only by the fixture generator to populate exFAT and NTFS images and
  plant alternate data streams), plus `umount`. Both scripts accept only regular files under `target/`,
  validate every argument, and refuse any `/dev/sd*`, `/dev/nvme*`, `/dev/mmcblk*` path.
  Prefer FUSE without root where it works (`ntfs-3g`, `exfat-fuse`) and keep the sudo path as fallback.
  👤 The owner adds a sudoers rule for exactly these two scripts (document the line in `docs/dev-setup.md`).
- Test: an image of each type (FAT32, exFAT, NTFS, ext4) is created, mounted read-only, a write attempt
  fails, unmount succeeds. On WSL, if exFAT or NTFS is missing from the kernel, the test must fail with an
  explicit message naming the missing module — then stop and tell the owner (choices: container, Debian bench,
  custom WSL kernel). Do not skip.

### WP-0.3 Requirements registry
- `tools/traceability/` (Python, part of the uv project, fully typed, tested).
- Generate `requirements.yaml` from `docs/spec.md` tables: id, level, phase(s), ANSSI, section, text.
  Add the reserved id `TOOLING` (level n/a) for tests of helpers, fixtures and tooling.
  NFR rows have no Phase column: take the phase from the plan's work packages that cite them.
  `tools/kit/req.py` shows how the tables are shaped; do not import it (it is a kit tool), re-implement
  properly with tests.
- Validation: JSON schema for the YAML, unique ids, every id cited in `docs/plan.md` exists.
- The registry is generated and committed; CI checks it is up to date (regenerate and diff).

### WP-0.4 Traceability tool
- Rust: a tiny proc-macro crate `crates/traceability` exporting `#[req("FR-06", ...)]`, a pass-through
  attribute that validates the id format (or `TOOLING`) at compile time and changes nothing else.
- Python: a pytest plugin (in `tools/traceability/`) registering the `req` marker, rejecting unknown ids
  (against `requirements.yaml`) at collection, and recording ids in the JUnit XML (`record_property`).
- Matrix generator: static scan of Rust sources for `#[req(...)]` above test functions + nextest JUnit
  results (`cargo nextest run --profile ci` with `junit` enabled) + pytest JUnit → `target/traceability.json`
  and a Markdown matrix. Unknown id → error.
- Rules (confirm with the owner before coding, they shape CI):
  1. Always: unknown ids fail; a requirement cited by a **ticked** WP in `docs/phase-status.md` without a
     passing test fails.
  2. `just trace --gate P<n>`: every MUST of phase P<n> without a passing test fails (used by `/phase-gate`);
     `just trace --gate all`: every MUST of the spec (used for the 1.0 release, WP-9.9).
  This matches the plan's "a MUST of the active phase without a passing test fails" at the moment it matters,
  without keeping CI red during the whole phase.
- Tests on fixture mini-repositories under `tests/tooling/fixtures/`: missing test fails; failing test fails;
  unknown id fails; complete repository passes.

### WP-0.5 Protobuf contracts and framing
- `proto/ostia/engine/v1/engine.proto` from spec §14 (plus `Limits`), `buf.yaml` with lint and breaking
  rules, `buf.gen.yaml`. Rust codegen with `prost` (build.rs or `buf generate`), Python with `protoc`
  via `grpcio-tools` or `buf` remote-free plugins — choose an offline-capable path and record it in an ADR.
- Framing (both languages): 4-byte big-endian length then message; cap (default 16 MiB, configurable);
  reject 0, > cap, truncated header, truncated body; a version check (`major` field or package) refusing
  other majors. No panic on any input (Rust: no `unwrap`, `proptest` on random bytes).
- Golden vectors in `proto/testdata/*.bin` + `*.json` description, generated once by a script, consumed by
  both test suites: Rust encodes == Python encodes, and each decodes the other's.
- CTR-03: every `AnalyzeResponse` carries engine id, engine version, content version — the decoder/validator
  rejects responses missing them.

### WP-0.6 Fuzz target
- `fuzz/` with `cargo-fuzz` (nightly only here: `cargo +nightly fuzz`). Target: the frame decoder.
- CI: short run per merge (e.g. 60 s), nightly long run with corpus caching. A seeded crash input in
  `fuzz/regressions/` replayed as a normal test proves crashes are caught (use a test-only decoder variant
  with a planted bug behind a `cfg(fuzzing_selftest)` flag, never in the real decoder).

### WP-0.7 Test doubles
- `tests/fakes/`: fake engine (a worker binary or script speaking the real framing: configurable hint,
  score, findings, delay, crash, garbage output, by sha256 or name pattern, from a JSON config),
  fake clock (Rust trait implementation + a file- or env-driven variant usable from the CLI in dev builds),
  fake collector and fake provider skeletons (HTTP servers with recorded behaviour; full contracts come in
  P6 and P8). Each double has behaviour tests.

### WP-0.8 Supply-chain gates
- `deny.toml` (licences allowlist: Apache-2.0, MIT, BSD-2/3, ISC, Unicode-3.0, Zlib, MPL-2.0 as file-level
  copyleft only if the owner agrees — ask 👤; sources: crates.io only; advisories: deny).
  After this package `deny.toml` is owner-gated (the guard hook blocks later edits).
- `cargo-audit`, `pip-audit` on hash-pinned requirements exported from `uv.lock`, CycloneDX SBOMs
  (`cargo cyclonedx`, `cyclonedx-py`). `just audit` runs them all.
- Tests: CI fails on a seeded disallowed licence (fixture crate depending on a fixture GPL crate via a
  path dependency) and on an unpinned Python requirement.

### WP-0.9 Test locking
The kit already provides the lock tool (`tools/lock/ostia_lock.py`), its self-tests, `rails.yml`,
`CODEOWNERS` and the agent instructions. This package wires them in:
- `just check` includes `verify-locks` and `kit-test`; CI runs `rails.yml` on every push and pull request.
- `docs/contracts/repository-settings.md`: the branch protection the owner must set on GitHub 👤
  (protect `main`, require a pull request with 0 required approvals — the owner opens the PRs the agent
  prepares, and GitHub forbids approving one's own PR —, require the `ci` and `rails` checks, no force push,
  tag rulesets restricting `lock-*` and `v*` to the owner, merge methods "rebase" or "merge commit" only).
- The plan's test ("changing a locked test without updating its manifest fails CI") is covered by
  `tools/kit/test_kit.py`; add a CI-level check in `tests/tooling/` that builds a temporary git repository
  at test time, locks a directory there with `ostia_lock.py lock` (allowed in a temp dir: the guard asks the
  owner once), modifies a locked file and expects `verify` to fail. Never commit a `LOCK.sha256` fixture.
- Red-first check (plan §2 step 4: "CI must show these tests failing"): `tools/ci/red_first.py` run on pull
  requests: for each `test(<REQ>)` commit, check it out in a worktree, run the tests it added, and require
  that they fail; require a later `feat(<REQ>)` commit for the same id. Its own tests come first.

### WP-0.10 Decision records
- `docs/adr/0001-...md` to `0013-...md` in MADR format from spec §21, each with context, decision,

### WP-0.11 Spike: usbsas
- Time-box: 2 sessions. Read-only evaluation: licence (GPLv3 → separate process only), process interface,

### WP-0.12 Lock: P1 acceptance tests → use `/phase-lock P1`
Before writing tests, land the contracts they rely on (own commits, reviewed with the lock):
1. `crates/ostia-cli` producing the `ostia` binary (clap). Subcommands exist and exit with code 3
   "not implemented: <cmd>" until built: `ostia scan`, `ostia policy verify`, `ostia version`.
2. `docs/contracts/cli.md`: proposed shape (refine, then owner review):
   `ostia scan --image <path> --report <out.json> [--policy <file> --policy-sig <file> --trust <pubkey>]
   [--mode compliant|selective|scan-only] [--max-scan-time <secs>] [--on-expiry <action>]
   [--dev-engine <fake-engine-config.json>]` (the `--dev-*` flags exist only with the `dev` cargo feature,
   never in release builds). Exit codes: 0 scan completed (verdict is in the report), 2 usage error,
   3 not implemented, 4 input refused (unsupported file system...), 5 internal error (fail closed).
3. `schemas/report.schema.json` v1: session, mode, medium (file system, size), objects as a tree
   (id, parent_id, origin, depth, path, size, sha256, sha1, detected_type, extension_mismatch, verdict,
   rule, score, explanation, engine_results), medium verdict (verdict, blocking objects, findings),
   policy (version, hash), timing (started, ended, expired, expiry action).
4. Policy signing: Ed25519 detached signature over the exact policy file bytes (no canonicalisation
   needed). Tests generate throwaway keys at runtime (Python `cryptography`, a test dependency).
5. `tests/acceptance/common/` (a package, imported as `from common import ...`; no `conftest.py` outside
   the phase directories): `run_ostia()`, `load_report()` (validates against the schema),
   `build_image()` (lazy import of the WP-1.3 generator), `fake_engine_config()`, `sign_policy()`.
   Check collection with `python3 tools/lock/ostia_lock.py collect p1`.

P1 acceptance tests must cover (see spec §20 and `req.py phase P1`): FR-03 (each of FAT12/16/32, exFAT,
NTFS, ext2/3/4 scanned; an unsupported file system refused with exit 4 and a clear message); FR-04 and
DEEP-05 (inventory counts, hidden files, NTFS alternate data streams listed and scanned, never marked
transferable); FR-05 and SEC-05 (type from content; renamed and double-extension files flagged and
SUSPICIOUS via R6); FR-06 (nested archives within limits fully listed; too deep, too dense, too large,
too many each UNSCANNABLE; malformed archive UNSCANNABLE, no crash); SEC-10 (hashes match the planted
content; report hashes equal the copy's hashes); FR-09 and the policy rules R1–R7 observable through the
fake engine (one test per rule and per precedence pair that can be exercised black-box: R1 beats all,
R2 beats R3, R3 beats R4–R6, ...); FR-10 (compliant mode: one MALICIOUS or UNSCANNABLE object blocks the
medium); FR-14 (expiry triggers the configured action and is reported — use budgets far smaller than
the fake engine's delay to avoid races); policy signature (unsigned or altered policy refused);
NFR-05 (a crashing or hanging fake engine yields UNSCANNABLE and the scan completes); exit criterion
(end-to-end scan of each image type without USB hardware).
Then 👤 review → `just lock p1` and `just lock common` → commit → tag `lock-p1` and `lock-common` and push
the tags → merge (see `GUIDE-FR.md` §6).
